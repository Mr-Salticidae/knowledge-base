# GPT / Codex 一直转圈、连不上？一份从症状到修复的完整排查手册

> 适用：你已经有能上外网的代理（机场 / Clash / Mihomo / v2rayN 之类），别的网站都正常，**偏偏 ChatGPT 网页转圈、Codex CLI 反复「正在重新连接」、Claude 桌面版一直加载**。本文按「症状 → 定位 → 修复」排，每一步都能照抄，全程只用系统自带的命令。所有数据来自真机实测，不是网上抄来的经验帖。

## 先说清楚：这篇能解决什么，不能解决什么

**能解决的**（技术链路层，占日常故障的绝大多数）：

- 代理明明开着，Codex CLI 却反复「正在重新连接 2/5」；
- 网页能打开、但回答吐一半就断，或者一直转圈不出字；
- 你的节点看起来延迟很低，用起来却慢得离谱；
- DNS 明明配了代理，实际却漏给了本地运营商。

**不能解决的**（账号层，任何脚本都碰不到）：

- 账号被封、被要求验证、反复触发风控。这一层取决于**账号出身**（注册时的国别、支付方式归属、账号年龄、是自己注册还是买的合租号），不取决于你今天用哪个节点。文末第七节专门讲这件事，那是本文最重要的一段。

**一句话定位**：本文帮你「别让一个本来正常的账号，因为技术疏漏白白卡住」，它造不出一个新的干净账号。

## 名词小抄（看不懂下文时回来查）

**代理客户端**
就是你装的那个上网工具，Clash Verge、Mihomo Party、v2rayN 都算。它负责把你的流量转发出去。

**节点**
机场给你的一条条线路，通常写成「日本 01」「香港 03」这样。每条线路的速度、出口国家、质量都不一样。

**系统代理模式**
代理客户端在系统里登记一个地址（一般是 `127.0.0.1:7890` 或 `127.0.0.1:7897`），**愿意读这个登记的程序**才会走代理。浏览器会读，很多命令行工具不会读。

**TUN 模式**
代理客户端在系统里装一块虚拟网卡，从内核层面接管**所有**流量。程序不需要知道代理存在，数据包自动进隧道。全局兜底能力最强。

**代理环境变量**
`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 这三个变量。命令行工具（Codex CLI、Claude Code、git、curl）不读系统代理登记，只认这几个变量。**它们和 TUN 是两条不同的路，同时开会出问题**——这是本文第一个也是最常见的坑。

**fake-ip**
Clash 系客户端的一种 DNS 加速模式：不真解析域名，而是随手发一个 `198.18.x.x` 开头的假地址给你，等你去连它时再在隧道里做真解析。副作用是**所有基于 IP 的检测手段全部失效**（详见第三节）。

**SSE / WebSocket 长连接**
AI 打字机效果靠的传输方式：连接建好后，服务器一小块一小块地往下吐字。它和普通网页请求的关键区别是——**对建立连接时的延迟极其敏感**。普通请求慢半秒你毫无感觉，长连接握手慢两三秒，客户端就会认为「连挂了」，开始重连。你看到的转圈，往往就是这个。

## 第一节 · 一分钟定位：你是哪一种转圈

先对号入座，再跳到对应章节，别从头改到尾。

| 你看到的现象 | 最可能的原因 | 去看 |
|---|---|---|
| Codex CLI 反复显示「正在重新连接 2/5」 | TUN 和代理环境变量同时开着，请求多走了一层 | 第四节 |
| 网页能开，回答吐一半就断 / 一直转圈不出字 | 同上，或者节点带宽太低 | 第四节 → 第五节 |
| 页面能开但极慢，加载几十秒 | 节点带宽垫底（延迟低也可能很慢） | 第五节 |
| 命令行工具全都连不上，浏览器却正常 | 没开 TUN，而命令行不读系统代理 | 第二节 |
| 提示「你所在的地区不受支持」 | 出口 IP 落在了不受支持的地区 | 第六节 |
| 微软商店装不上 ChatGPT 桌面版 | 商店地区 / 分发链路，不是网络故障 | 第六节 |
| 时好时坏，昨天好好的今天又崩 | 配置改了没落盘，重启后回滚了 | 第八节 |

## 第二节 · 先搞清楚：你的流量到底怎么出去的

这是所有排查的地基。**同一个症状，在 TUN 模式和系统代理模式下，修法完全相反**，所以必须先确认自己在哪一档。

打开 PowerShell（开始菜单搜 PowerShell，回车即可），依次运行：

```powershell
# 1. 代理端口是不是真的在听（把 7897 换成你客户端里显示的端口）
netstat -ano | findstr ":7897"

# 2. 有没有 TUN 虚拟网卡（有输出＝TUN 开着）
ipconfig | findstr /i "tun"

# 3. 系统代理登记了没有
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyEnable
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyServer
```

对照下表认清自己：

| 你的档位 | 特征 | 浏览器 | Codex CLI / Claude Code / 桌面应用 |
|---|---|---|---|
| **只开系统代理** | 有代理端口，无 TUN 网卡 | 正常 | **直连暴露真实 IP，或者干脆连不上** |
| **只开 TUN** | 有 TUN 网卡 | 正常 | 正常（内核层全接管） |
| **两个都开** | 两样都有 | 正常但多绕一层 | **最容易转圈的组合**，见第四节 |

**为什么命令行工具会掉队**：浏览器和 .NET 程序会主动去读系统里那条代理登记，而 Node / Rust / Go 写的命令行工具（Codex CLI、Claude Code CLI）和 Electron 应用的主进程**根本不读**，它们只认前面说的那三个环境变量。所以「浏览器好好的，Codex 连不上」不是玄学，是设计如此。

**推荐的基线配置**（省掉后面 80% 的麻烦）：

- **优先开 TUN**，同时**不要**设任何用户级代理环境变量。一劳永逸，所有程序都被兜住。
- 如果客户端不支持 TUN、或者你不想开，那就只开系统代理，**再单独给命令行工具设环境变量**——这种情况下环境变量是必需的，不是多余的。

## 第三节 · 三条铁律：这几种自检方式是假的

在动手改任何设置之前，先把三个错误的判断方式扔掉。很多人卡住不是因为不会修，是因为**一直在看假信号**。

### 铁律一：ping 通不等于能用

在 fake-ip 模式下，域名被解析成 `198.18.x.x` 这样的本地虚拟地址，ICMP 由你自己的电脑应答。结果是：

- ping 任何域名都秒通，延迟接近 0；
- **节点完全挂掉，ping 结果一模一样**。

也就是说，你拿 ping 当健康信号，恰恰因为它**永远是绿的**。看到解析结果是 `198.18.` 开头，就该知道 `ping`、`tracert`、`nslookup` 这一层全部失去意义。

怎么看解析结果：

```powershell
Resolve-DnsName chatgpt.com
```

### 铁律二：客户端面板上的延迟数字不等于速度

Clash 那个「延迟测试」测的是一次握手往返，**完全不测吞吐量**。真机实测过一批节点，两者几乎不相关：

| 节点 | 延迟排名 | 带宽排名 |
|---|---|---|
| 日本 01 | 8 / 34 | **14 / 14（垫底）** |
| 日本 10 | 5 / 34 | 13 / 14 |
| 印度 01 | 10 / 34 | 4 / 14 |
| 香港 03 | 1 / 34 | 3 / 14 |

那个延迟排第 8、看起来完全正常的「日本 01」，实测带宽只有 **2.72 Mbps**——连 480p 都紧张。如果你按面板上的绿色数字选节点，它排在中上游，你永远不会怀疑它。

**判据**：延迟只用来做第一轮淘汰（筛掉超时的），不用来排序。要看快慢，实测吞吐。

### 铁律三：测 `api.openai.com` 正常，不代表 Codex 正常

Codex CLI 和 ChatGPT 桌面版的请求打的是 **`chatgpt.com/backend-api/...`**，不是 `api.openai.com`。这两个域名走不同的 CDN 路径，延迟能差好几倍。

真实排查里出现过这样一幕：先测 `api.openai.com`，延迟 0.85 秒，一切正常，差点收工；换到真实端点一测，问题立刻现形：

| 端点 | TLS 握手 | 首字节 |
|---|---|---|
| `api.openai.com/v1/models` | 0.85s | 1.24s |
| `chatgpt.com/backend-api/codex/models` | 2.54s | **3.83s** |
| WebSocket 端点 | **3.47s** | **4.57s** |

那个 4.57 秒的 WebSocket 端点，正是日志里反复重连的那个连接。

**判据**：诊断「某个应用网络慢」时，要测这个应用**实际请求的地址**，不能凭直觉假设。

## 第四节 · 头号元凶：TUN 和代理环境变量同时开着

如果你的症状是 **Codex CLI 反复「正在重新连接」**，或者**回答吐一半就断**，先查这一条，命中率最高。

### 它是怎么发生的

很多教程会让你「设一下代理环境变量」，你照做了；后来你又开了 TUN。两件事单独看都没错，**加起来就变成了双重路由**：

```
你的实际路径：Codex → HTTP 隧道(127.0.0.1:7890) → 代理内核解析 → TUN 虚拟网卡 → 出国 → 目标
本该走的路径：Codex → TUN 虚拟网卡 → 出国 → 目标
```

多出来的那层 HTTP 隧道要额外做一次本地连接、一次请求解析、一次队列调度。对普通请求，代价是多 0.4 秒，你感觉不到；**对 WebSocket 握手，代价是多 3.9 秒**——而客户端的超时重连逻辑就在这个区间。于是你看到「正在重新连接 2/5」。

真机对照实测（同一台机器，只改这一个变量）：

| 端点 | 有环境变量 | 删掉环境变量 | 改善 |
|---|---|---|---|
| WebSocket 重连端点 | 4.57s | **0.70s** | **85% ↓** |
| codex/models 接口 | 2.30s | 1.47s | 36% ↓ |
| usage 接口 | 2.01s | 1.01s | 50% ↓ |

这不是「快了一点」，是**从「必然超时重连」变成「稳定不重连」的质变**。

### 怎么查

```powershell
reg query "HKCU\Environment" /v HTTP_PROXY
reg query "HKCU\Environment" /v HTTPS_PROXY
reg query "HKCU\Environment" /v ALL_PROXY
```

**有输出**（显示出 `http://127.0.0.1:7890` 之类）＝设了。**报「找不到指定的注册表项或值」**＝没设，那这条不是你的问题，跳到第五节。

### 怎么修

**先确认你的 TUN 是开着的**（第二节的第 2 条命令有输出）。TUN 开着时，这三个变量是**冗余的负担而不是安全保障**——内核已经接管了全部流量，它们只会让请求多绕一圈。

```powershell
reg delete "HKCU\Environment" /v HTTP_PROXY /f
reg delete "HKCU\Environment" /v HTTPS_PROXY /f
reg delete "HKCU\Environment" /v ALL_PROXY /f
```

**关键的最后一步：把所有终端窗口全部关掉再重开。** 已经运行的进程不会感知到注册表改动，你在原来那个窗口里再跑 Codex，看到的还是老样子——很多人卡在这里，以为「删了没用」。

验证问句不是「现在好了吗」，而是「**重启终端后还正常吗**」。

### 反过来的情况

如果你**没开 TUN、只开了系统代理**，那这三个变量恰恰是必需的——删了命令行工具就直连了。这种情况下正确做法是：

- 要么去客户端里把 TUN 打开，然后删掉变量（推荐）；
- 要么保留变量，但别再开 TUN，二选一。

### 怎么自己测出快慢差别

这是判断代理层加了多少成本的**金标准**，两个字段就够：

```powershell
curl.exe -o NUL -s -w "TLS握手 %{time_appconnect}s  首字节 %{time_starttransfer}s  状态 %{http_code}\n" https://chatgpt.com/backend-api/codex/models
```

- `time_appconnect`＝TLS 握手完成用了多久（含代理隧道那一跳）；
- `time_starttransfer`＝第一个字节到达用了多久。

改设置前后各跑三五次取平均，一对比就知道有没有效果。**注意看 `http_code`**：这里返回 401 是正常的（没带凭据），我们只关心时间。

## 第五节 · 第二元凶：节点选错了

如果环境变量那条没命中，或者删掉之后还是慢，那多半是节点本身的带宽不够。

AI 对话是流式输出，它对**稳定的小带宽**要求不高，但对**握手延迟**和**连接稳定性**很敏感；而如果你还要看视频、传图片，带宽就直接决定体验。参考值：720p 视频大约需要 3 Mbps。

### 用浏览器粗测（最简单）

在**当前节点**下，浏览器打开 `speed.cloudflare.com`，跑完看下行速度。低于 5 Mbps 的节点就别用了。

### 用命令行精测（推荐，能看到握手时间）

```powershell
curl.exe -o NUL -s -w "TLS握手 %{time_appconnect}s  下行 %{speed_download} B/s\n" https://speed.cloudflare.com/__down?bytes=52428800
```

**换一个节点，再跑一次，对比着看。** 别一次测十几个，先测你常用的三四个。

### 一个必须知道的坑：改了不等于存下来了

通过客户端界面切了节点、或者用脚本调接口切了节点，**可能只改了内存里的运行状态，没写回配置文件**。表现是：当时确实变快了，**重启电脑后又变回原样**，而你不会把「重启」和「变慢」联系起来，只会觉得「上次修好了，怎么又坏了」。

**处置**：在客户端界面里**手动点一次**你要的节点（而不是只靠脚本或自动切换），然后重启客户端，确认它还停在那个节点上。

**验证问句统一成「重启后还在吗」，而不是「现在生效了吗」。**

## 第六节 · 其他几种症状

### 症状：提示「你所在的地区不受支持」

这说明你的**出口 IP** 落在了对方不支持的地区。检查你现在从哪出网：

```powershell
curl.exe https://ipinfo.io/json
```

看 `country` 字段是不是你以为的那个国家。常见情况是节点自动切换、或者某个规则把这个域名走了直连。

**正确处置**：换一个受支持地区的节点。

**错误处置**（下一节详说）：改系统地区、改时区、伪装身份。这不解决问题，还会引入新麻烦。

### 症状：微软商店装不上 ChatGPT 桌面版

这是**分发链路**问题，不是网络故障，别急着改网络设置。按顺序排：

1. **先记录完整报错原文**，不要只记「装不上」。「此产品在你的市场中未提供」和「下载一直转圈」是两回事；
2. 核对系统版本够不够（ChatGPT Windows 版要求 Windows 10 的 17763.0 或更高，`winver` 可查）；
3. 核对是不是公司 / 学校设备——组织的商店策略可以直接禁止安装；
4. 只从官方下载页或微软商店拿安装包，不要用第三方重打包版本。

有一种情况确实是网络：微软商店的下载**不走 `127.0.0.1` 这类本地代理地址**，所以只开系统代理时它可能下不动，而**开 TUN 后能下**。这是「该环境下的有效修复」，不是「所有商店应用都必须开 TUN」的定律。

### 症状：DNS 看着走了代理，实际漏给了本地运营商

表现通常不是「打不开」，而是「解析慢、偶发连错、隐私上不干净」。这一层的坑最深，给你四步起手式：

**第一步：列出所有网卡的 DNS。**

```powershell
Get-DnsClientServerAddress -AddressFamily IPv4 | Format-Table -AutoSize
```

看到 `114.114.114.114`、`223.5.5.5` 这类国内公共 DNS 挂在**物理网卡**上，就是一条潜在绕行道。Windows 会**同时向每一块启用的网卡的 DNS 发查询**，发向物理网卡那条**根本不经过 TUN**，代理的 DNS 劫持看不见它。

**第二步：查客户端配置里 `fake-ip-filter` 有没有一条 `"*"`。** 这是黑名单，写了 `*` 等于**所有域名都不用 fake-ip**——配置上写着 `enhanced-mode: fake-ip`，实际形同虚设。

**第三步：确认你改的是会生效的那一层。** 很多 GUI 客户端有三层配置（内核设置 / 应用设置 / 每次自动生成的运行配置），**改到自动生成的那层等于没改**，重启就没了。改完重启一次客户端，再回头确认字段还在。

**第四步：主动实测收尾。** 静态检查全绿也可能在漏，只有实测能证伪。用 `dnsleaktest.com` 或 `bash.ws` 跑一次扩展检测，看**实际应答你的解析器**都在哪个国家。它们全在你的出口国＝干净；有一个在国内＝在漏。

真机案例：一台配置「看起来完全正常」的机器，实测出来 **3 个应答解析器全在中国大陆**，而出口在香港。修了五轮才全绿——每一轮都靠实测逼出下一层。

## 第七节 · 三条安全边界（比修网络更重要）

这一节讲的是**不要做的事**。它比前面所有修法都重要，因为前面修错了顶多白忙，这里做错了会掉账号。

### 边界一：别用「伪装地区 / 伪装时区」当防封号手段

网上流传很多说法：「系统时区必须和出口 IP 一致否则封号」「中文语言会触发封号」「改 Windows 地区能解决一切」。这些**没有任何官方依据**。

真实情况是：**让浏览器指纹（时区、语言）和出口国保持一致，是为了别露出破绽**——IP 显示在东京、浏览器却报 UTC+8 加中文，稍讲究的风控一眼就能看出你在用代理。这是**减分项管理**，不是**免死金牌**。

而官方在你收到可疑活动提醒时给的建议，反而经常是：**停用 VPN / 代理、退出全部设备、改密码、开两步验证，然后在单一可信设备和网络上重试**。方向和「伪装得更像」正好相反。

**同时**：只有你**确实长期迁居**才应该去改 Windows 的地区设置，那会影响商店余额、订阅和已购内容。别把它当成通用的安装按钮。

### 边界二：403 不等于「你的 IP 被风控了」

HTTP 403 只说明**请求到达了一个会返回 403 的服务端或边缘节点**。它可能和代理、IP 地理位置、可疑流量有关，但**单次 403 不能独立证明什么**。要定性，得结合页面正文、Cloudflare 的 Ray ID、发生时间。

同理，看到 DNS 返回 `198.18.x.x` 不要惊慌，那是 fake-ip 的内部映射，**不是泄露**。真正的异常长这样：解析结果落在**明显属于其他大厂的 IP 段**（比如查 `chatgpt.com` 返回了 Meta 的地址）——那才是解析被投毒。

### 边界三：账号出身那一层，任何工具都碰不到

这是本文最重要的一段，也是最反直觉的一段。

风控几乎都是**累加计分 + 阈值触发**，不是单点判死。真正决定生死的因素按权重排：

| 权重 | 因素 | 工具能做什么 |
|---|---|---|
| 1 | 出口 IP 的共享密度与信誉 | 只覆盖一半：能判是不是机房段，但**测不出这个 IP 背后挂了多少个账号** |
| 2 | **账号出身**（注册时的国别、支付归属、账号年龄、自注册还是买号） | **完全碰不到** |
| 3 | 行为模式（国家跳变、一号多设备、并发） | 能管：固定节点、别乱切 |
| 4 | 技术指纹（时区 / 语言 / WebRTC / DNS） | 能管：本文前六节 |

**第 2 层是高权重因素里、工具唯一完全碰不到的一层**，而它恰好解释了那个经典疑问：「同样用代理，为什么有人从没出过事、有人反复被封？」

答案是：风控对**老账号**建的是「这个账号的正常长什么样」（per-account baseline），对**新账号**只能用「这类特征的人一般是什么货色」（population prior）。

> **一个用了很多年、有连续良性历史的号，「从代理 IP 登录」早就写进了它的基线，不构成异常；一个上周为了注册而新建的号没有基线可比，只能落到人群先验上，而机房 IP 段的人群先验极差。**

有个真实的实测数据能说明这件事有多反直觉：一位作者长期使用的那个节点，实测出口是 **DigitalOcean**（风控黑名单上最经典的机房段之一），**账号从未出过事**——因为那个账号是 2018 年注册的，「中国 + 代理」这个组合从第一天起就是它的常态。

**结论要反过来读**：拿到「我的号一直没事」这个观测，直觉是「所以我可以随便折腾」。恰恰相反——

> **你的账号不是抗封的，是不可替代的。**

抗封意味着可再生，丢了再弄一个。但一个多年老号的价值全部来自不可压缩的时间，真封了你不可能「再注册一个 2018 年的账号」。所以理性的做法是：**信任资产越厚，越该省着用。**

反过来，如果你的号反复被封而技术修法全都没帮上忙，问题多半就在第 2 层——那不是脚本能解决的。

## 第八节 · 想省事？用一键体检脚本

上面那些检查，有一个开源工具可以一次性全跑完，Windows 和 macOS / Linux 都能用：

**vpn-guard**：`https://github.com/Mr-Salticidae/vpn-guard`（MIT 协议，PowerShell / Bash 双版本，零依赖）

### 用法一：一键自查（只读，不改你任何系统设置）

```powershell
# Windows：下载解压后，在脚本所在目录打开 PowerShell
powershell -ExecutionPolicy Bypass -File .\vpn-leak-audit.ps1
```

```bash
# macOS / Linux
./vpn-leak-audit.sh
```

它会用红 / 黄 / 绿输出八项，正好覆盖本文前六节：

| 项 | 查什么 | 对应本文 |
|---|---|---|
| 0 | 代理客户端与流量接管方式（TUN / 系统代理 / 都没有） | 第二节 |
| 1 | 公网出口 IP、地理位置、是不是机房段 | 第六节 |
| 2 | **命令行 / 桌面应用的出口**（Codex、Claude 走的就是这条） | 第二、四节 |
| 3 | IPv6 有没有绕过代理 | — |
| 4 | 系统时区和出口国差几个小时 | 第七节 |
| 5 | 浏览器语言和出口国一致吗 | 第七节 |
| 6 | DNS 解析路径 + **DNS 泄露主动实测** | 第六节 |
| 7 | WebRTC 泄露面（需另开检测页） | — |
| 8 | **链路质量：握手耗时 + 实际吞吐，够不够看 720p** | 第五节 |

**第 2 项最值得看**——它用 `curl --noproxy '*'` 复刻「一个完全不认代理设置的程序」去请求，再和浏览器侧的出口比对。两者不一致，就说明你的 Codex / Claude 正在绕过代理直连。这一项是被动检查看不出来的：注册表里代理开着、浏览器一切正常，而那些程序根本不读它。

### 用法二：给 Codex / Claude 单独套一层一致的环境

```powershell
powershell -ExecutionPolicy Bypass -File .\app-vpn.ps1 -List   # 看支持哪些应用
powershell -ExecutionPolicy Bypass -File .\app-vpn.ps1 codex   # 在一致环境里跑 Codex CLI
powershell -ExecutionPolicy Bypass -File .\app-vpn.ps1 claude  # Claude Code CLI
```

它只给**被它启动的那一个进程**注入代理、时区、语言，进程退出就还原，**不写任何系统级设置**。适合「没开 TUN、只有系统代理」的场景。

**注意它的边界**：它靠环境变量约定生效，前提是目标程序愿意读。绝大多数 Node / Rust / Go / Python 生态的工具都读，但**硬编码直连、自带网络栈的程序它管不住**。要对任意程序都强制生效，只有 TUN 模式。

### 用法三：自动挑节点（有一个必须知道的风险）

仓库里还有 `auto-select-node.ps1`，能自动按「安全 + 带宽」筛选并切换节点。

> ⚠️ **扫描过程本身会把你的全局出口逐个切过每一个候选节点**（默认十几次，包括随后才被淘汰的）。也就是说，跑一次扫描，你的账号会在几分钟内经历一串跨国跳变——这正是前面权重表里第 3 层的「国家跳变」。**如果你正开着 ChatGPT / Claude 的会话，别跑它**；跑完再登录。加 `-DryRun` 也一样会切。

### 顺手提醒两个小坑

- **别把带中文的 `.ps1` 存成无 BOM 的 UTF-8**。Windows PowerShell 5.1 会按 GBK 去读，中文全角标点被错读成别的 token，脚本直接解析失败，报错行还全指在中文注释上，极具迷惑性。存成「UTF-8 with BOM」即可。
- **一次只改一个变量**。开 TUN、换节点、改 DNS 三件事同时做，事后你无法归因是哪一件修好的，下次复发只能从头再来。

## 一页速查

按这个顺序走，不要跳：

1. **先看接管方式**：`ipconfig | findstr /i "tun"` 有没有 TUN；系统代理开没开。
2. **扔掉假信号**：ping 通不算数；面板延迟不代表速度；`api.openai.com` 正常不代表 Codex 正常。
3. **查双重路由**：`reg query "HKCU\Environment" /v HTTP_PROXY`。TUN 开着又有这个＝元凶，删掉，**关掉所有终端重开**。
4. **测真实端点**：`curl.exe -o NUL -s -w "%{time_appconnect} %{time_starttransfer}\n" https://chatgpt.com/backend-api/codex/models`，改前改后各测几次对比。
5. **实测节点带宽**：`speed.cloudflare.com`，低于 5 Mbps 换掉。**换完在客户端界面手点一次**，确认重启后还在。
6. **查 DNS**：`Get-DnsClientServerAddress`，物理网卡挂着 114 之类的就是绕行道；再用 `dnsleaktest.com` 主动实测收尾。
7. **地区问题看出口**：`curl.exe https://ipinfo.io/json` 看 `country`，换节点，**别改系统地区、别伪造时区**。
8. **搞不定就跑一键体检**：`vpn-leak-audit.ps1`，八项红黄绿一次看完。
9. **账号层的事别指望技术修法**。收到安全提醒，按官方流程来：退出全部设备、改密码、开两步验证、在单一可信设备和网络上重试。

## 最后一句

这份手册里所有的数字都来自真机实测，而实测的价值恰恰在于——**它推翻了好几个「看起来完全合理」的判断**：延迟低的节点带宽垫底、配置写着 fake-ip 而 fake-ip 形同虚设、加了代理环境变量反而让请求变慢、静态检查全绿而 DNS 其实一直在漏。

所以最该带走的不是某一条命令，而是那个习惯：**别信声明，别信面板上的绿色，去测你真正在走的那条链路。**
