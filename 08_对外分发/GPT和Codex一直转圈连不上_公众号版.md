那天的现象很具体：Codex CLI 每敲一条指令，界面就开始转，转几秒跳出一行「正在重新连接 2/5」，然后 3/5、4/5。浏览器一切正常，B 站能刷，GitHub 能开，测速软件跑出一百多兆。

按常理，这时候该怀疑机场。换节点、换协议、重启客户端，全试了一轮，没用。

后来定位到的根因，和「机场好不好」一点关系都没有。修法是删掉三个环境变量，那个反复超时的连接从 4.57 秒变成 0.70 秒。

这篇把整个排查过程写出来，包括中间那些把我们带偏的岔路。所有数字都是真机实测的，不是网上抄的经验帖。

## 一、先说最可能的那个元凶

如果你的症状是「命令行工具反复重连」或者「网页回答吐一半就断」，先查这一条，命中率最高。

它叫**双重路由**，成因是两件本身都没错的事撞在了一起。

第一件：很多教程会让你设一下代理环境变量。就是 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 这三个。这么做是有道理的——浏览器会主动去读系统里那条代理登记，而 Node、Rust、Go 写的命令行工具根本不读，它们只认这三个变量。不设，Codex CLI 和 Claude Code 就是裸奔状态。

第二件：后来你在客户端里打开了 TUN 模式。TUN 会在系统里装一块虚拟网卡，从内核层面接管所有流量，程序不需要知道代理存在。

单独看，两件都对。加起来就变成了这样：

```
你实际走的：Codex → HTTP 隧道(127.0.0.1:7890) → 代理内核 → TUN 网卡 → 出国
本该走的　：Codex → TUN 网卡 → 出国
```

多出来的那层 HTTP 隧道，要额外做一次本地连接、一次请求解析、一次队列调度。

对普通网页请求，这个代价是多 0.4 秒，你根本感觉不到。真正出事的是另一类连接。

AI 的打字机效果靠的是 SSE 和 WebSocket 这类长连接，它和普通请求有个致命区别：**握手阶段没有任何数据流过**，客户端没法区分「正在握手」和「连接已经挂了」，只能靠超时阈值判断。多出来的这一跳，让 WebSocket 握手从 0.70 秒涨到 4.57 秒——正好跨过了 Codex 的重连阈值。

于是你看到的是转圈，实际发生的是它一次次以为自己掉线了。

同一台机器，只改这一个变量，前后对照：

| 端点 | 有环境变量 | 删掉之后 |
|---|---|---|
| WebSocket 重连端点 | 4.57s | 0.70s |
| codex/models 接口 | 2.30s | 1.47s |
| usage 接口 | 2.01s | 1.01s |

这不是快了一点。这是从「必然超时重连」变成「稳定不重连」。

查法，在 PowerShell 里跑三行：

```powershell
reg query "HKCU\Environment" /v HTTP_PROXY
reg query "HKCU\Environment" /v HTTPS_PROXY
reg query "HKCU\Environment" /v ALL_PROXY
```

有输出就是设了。再确认你的 TUN 是开着的：

```powershell
ipconfig | findstr /i "tun"
```

两个都有，就是它。TUN 开着的时候，那三个变量是纯粹的负担——内核已经把所有流量接管了，它们只会让请求多绕一圈。删掉：

```powershell
reg delete "HKCU\Environment" /v HTTP_PROXY /f
reg delete "HKCU\Environment" /v HTTPS_PROXY /f
reg delete "HKCU\Environment" /v ALL_PROXY /f
```

然后是最容易被跳过的一步：**把所有终端窗口全部关掉再重开**。已经在运行的进程不会感知到注册表改动，你在原来那个窗口里再跑一次 Codex，看到的还是老样子。很多人卡在这里，以为「删了没用」。

验证的问句不是「现在好了吗」，是「重启终端之后还正常吗」。

反过来说，如果你没开 TUN、只开了系统代理，那这三个变量恰恰是必需的，删了命令行工具就直连了。这种情况下正确的做法是去客户端里把 TUN 打开、再删变量，或者保留变量、别开 TUN，二选一。

## 二、为什么你之前一直没查出来

上面那个根因，说破了并不复杂。真正花时间的是前面那段——我们一开始查的方向全是错的，因为手上三个最顺手的信号，全是假的。

**第一个假信号：ping 通。**

Clash 系客户端有个 fake-ip 模式，它不真解析域名，而是随手发一个 `198.18.x.x` 开头的假地址给你，等你去连的时候再在隧道里做真解析。副作用是 ICMP 由你自己的电脑应答，于是 ping 任何域名都秒通、延迟接近零。

关键在于：节点完全挂掉，ping 结果一模一样。

你拿它当健康证明，恰恰因为它永远是绿的。看到解析结果是 `198.18.` 开头，就该知道 ping、tracert、nslookup 这一整层已经全部失去意义了。

**第二个假信号：客户端面板上的延迟数字。**

那个「延迟测试」测的是一次握手往返，完全不测吞吐量。我们实测过一批节点，两者几乎不相关：延迟排第 8、看起来完全正常的那个「日本 01」，实测带宽只有 2.72 Mbps，连 480p 都紧张。而延迟排第 1 的香港节点，带宽也在前三。

如果你按面板上的绿色数字选节点，那个 2.72 Mbps 的节点排在中上游，你永远不会去怀疑它。

**第三个假信号：测了 `api.openai.com`，正常。**

这个最阴。我们第一轮就是这么测的，延迟 0.85 秒，一切正常，差点收工。

后来去翻 Codex 的日志才发现，它的请求根本不打 `api.openai.com`，打的是 `chatgpt.com/backend-api/...`。换到真实端点一测，问题立刻现形：TLS 握手 2.54 秒，首字节 3.83 秒，而那个 WebSocket 端点是 4.57 秒。

同一个服务的不同域名，走不同的 CDN 路径、不同的 TLS 配置，延迟能差好几倍。

三个假信号有个共同点：**它们都很容易取用，而且都倾向于给你绿灯**。诊断的时候，最方便的那个信号往往最不可信。

想测得准，其实只要两个字段：

```powershell
curl.exe -o NUL -s -w "TLS握手 %{time_appconnect}s  首字节 %{time_starttransfer}s\n" https://chatgpt.com/backend-api/codex/models
```

`time_appconnect` 是 TLS 握手完成用了多久，含代理隧道那一跳；`time_starttransfer` 是第一个字节到达用了多久。改设置前后各跑三五次取平均，一对比就知道有没有效果。返回 401 是正常的，我们只看时间。

## 三、如果不是它

删完环境变量还是慢，那接着往下两层看。

**节点带宽不够。** 在当前节点下用浏览器打开 speed.cloudflare.com 跑一次，低于 5 Mbps 就别用了，720p 视频大约需要 3 Mbps。

这里有个隐藏的坑：你在界面上切了节点，可能只改了内存里的运行状态，没写回配置文件。表现是当时确实变快了，重启电脑之后又变回原样，而你不会把「重启」和「变慢」联系起来，只会觉得上次修好了怎么又坏了。所以换完节点，在客户端界面里手动点一次，重启客户端，确认它还停在那儿。

**DNS 漏给了本地运营商。** 这一层的表现通常不是打不开，而是解析慢、偶发连错。起手式四步：

先列出所有网卡的 DNS：

```powershell
Get-DnsClientServerAddress -AddressFamily IPv4 | Format-Table -AutoSize
```

看到 `114.114.114.114` 这类国内公共 DNS 挂在物理网卡上，就是一条绕行道——Windows 会同时向每一块启用的网卡的 DNS 发查询，发向物理网卡那条根本不经过 TUN，代理的 DNS 劫持看不见它。

第二步查客户端配置里 `fake-ip-filter` 有没有一条 `"*"`。那是黑名单，写了 `*` 等于所有域名都不用 fake-ip，配置上写着开了，实际形同虚设。

第三步确认你改的是会生效的那一层。很多 GUI 客户端有三层配置（内核设置、应用设置、每次自动生成的运行配置），改到自动生成的那层等于没改，重启就没了。

第四步用 dnsleaktest.com 主动实测收尾，看实际应答你的解析器都在哪个国家。我们那台机器静态检查全绿，实测出来三个应答解析器全在国内，而出口在香港。修了五轮才全绿，每一轮都靠实测逼出下一层。

## 四、有三件事，做了只会更糟

网上流传很多「防封号」的说法：系统时区必须和出口 IP 一致否则封号、中文语言会触发封号、改 Windows 地区能解决一切。

这些没有任何官方依据。

让浏览器的时区和语言跟出口国保持一致，是有意义的——IP 显示在东京、浏览器却报 UTC+8 加中文，稍讲究的风控一眼就能看出你在用代理。但那是减分项管理，不是免死金牌。而官方在你收到可疑活动提醒时给的建议，方向恰恰相反：停用代理、退出全部设备、改密码、开两步验证，然后在单一可信设备和网络上重试。

至于改 Windows 的地区设置，只有你确实长期迁居才应该动它，那会影响商店余额、订阅和已购内容。别把它当成通用的安装按钮。

第二件：看到 403 就断定「我的 IP 被风控了」。403 只说明请求到达了一个会返回 403 的服务端，它可能和代理、地理位置、可疑流量有关，但单次 403 什么也证明不了。要定性得看页面正文、Cloudflare 的 Ray ID、发生时间。

第三件：同时改三样东西。开 TUN、换节点、改 DNS 一起做，好了你也不知道是哪件修好的，下次复发只能从头再来。一次只改一个变量，改完把上面那几条命令重跑一遍。

## 五、想省事，有个开源工具能一次跑完

上面这些检查，我们顺手做成了一个开源工具箱，叫 **vpn-guard**，GitHub 上搜作者名 Mr-Salticidae 就能找到。MIT 协议，PowerShell 和 Bash 双版本，零依赖，Windows 和 macOS / Linux 都能用。

主力是一条只读命令，不改你任何系统设置：

```powershell
powershell -ExecutionPolicy Bypass -File .\vpn-leak-audit.ps1
```

它会用红黄绿输出八项：流量接管方式、出口 IP 和归属、命令行与桌面应用的出口、IPv6、时区一致性、语言、DNS 解析路径加主动实测、WebRTC、链路质量。

最值得看的是第 2 项。它用 `curl --noproxy '*'` 复刻一个「完全不认代理设置的程序」去请求，再和浏览器侧的出口比对。两者不一致，就说明你的 Codex 和 Claude 正在绕过代理直连。这一项是被动检查看不出来的：注册表里代理开着、浏览器一切正常，而那些程序压根不读它。

另外还有个 `app-vpn`，专门给桌面应用和命令行用：

```powershell
powershell -ExecutionPolicy Bypass -File .\app-vpn.ps1 codex
```

它只给被它启动的那一个进程注入代理、时区、语言，进程退出就还原，不写任何系统级设置。

有一条风险得说在前面。仓库里还有个自动挑节点的脚本，扫描过程本身会把你的全局出口逐个切过每一个候选节点，默认十几次。也就是说跑一次扫描，你的账号会在几分钟内经历一串跨国跳变。如果你正开着 ChatGPT 或 Claude 的会话，别跑它，跑完再登录。

## 最后一件事，可能比上面所有内容都重要

写到这儿都是技术链路的事。但如果你的困扰是账号反复被封、总是被要求验证，那上面每一条修法都帮不上忙——因为那不在同一层。

风控几乎都是累加计分加阈值触发，不是单点判死。真正决定生死的因素按权重排下来，第一是出口 IP 的共享密度和信誉，第二是账号出身，第三是行为模式，第四才是时区语言这类技术指纹。

前面整篇文章解决的是第四层，vpn-guard 能碰到第三、第四层，第一层只能覆盖一半——它能判断这个 IP 是不是机房段，但测不出这个 IP 背后挂了多少个账号。

第二层，任何工具都完全碰不到。

而恰恰是第二层，解释了那个经典疑问：同样用代理，为什么有人从没出过事，有人反复被封。

答案是风控对老账号建的是「这个账号的正常长什么样」，对新账号只能用「这类特征的人一般是什么货色」。一个用了很多年、有连续良性历史的号，「从代理 IP 登录」早就写进了它的基线，不构成异常；一个上周为了注册而新建的号没有基线可比，只能落到人群先验上，而机房 IP 段的人群先验极差。

有个实测数据能说明这事有多反直觉：我们查了作者长期用的那个节点，出口是 DigitalOcean——风控黑名单上最经典的机房段之一。而那个账号从 2018 年用到现在，从没出过事。因为「中国加代理」这个组合，从它注册的第一天起就是它的常态。

所以拿到「我的号一直没事」这个观测，直觉结论是「所以我可以随便折腾」。恰恰相反。

你的账号不是抗封的，是不可替代的。

抗封意味着可再生，丢了再弄一个。但一个多年老号的价值全部来自不可压缩的时间——真封了，你不可能再注册一个 2018 年的账号。

结论反过来读：信任资产越厚，越该省着用。

## 附：能直接抄的九步

1. 先看接管方式：`ipconfig | findstr /i "tun"` 有没有 TUN，系统代理开没开。
2. 扔掉三个假信号：ping 通不算数，面板延迟不代表速度，`api.openai.com` 正常不代表 Codex 正常。
3. 查双重路由：`reg query "HKCU\Environment" /v HTTP_PROXY`。TUN 开着又有这个，就是元凶，删掉，然后关掉所有终端重开。
4. 测真实端点：`curl.exe -o NUL -s -w "%{time_appconnect} %{time_starttransfer}\n" https://chatgpt.com/backend-api/codex/models`，改前改后各测几次。
5. 实测节点带宽：speed.cloudflare.com，低于 5 Mbps 换掉；换完在客户端界面手点一次，确认重启后还在。
6. 查 DNS：`Get-DnsClientServerAddress`，物理网卡挂着 114 之类的就是绕行道，再用 dnsleaktest.com 实测收尾。
7. 地区问题看出口：`curl.exe https://ipinfo.io/json` 看 country，换节点，别改系统地区、别伪造时区。
8. 搞不定就跑一键体检：vpn-leak-audit，八项红黄绿一次看完。
9. 账号层的事别指望技术修法。收到安全提醒按官方流程来：退出全部设备、改密码、开两步验证、在单一可信设备和网络上重试。

这份手册里所有数字都来自真机实测，而实测的价值恰恰在于它推翻了好几个「看起来完全合理」的判断：延迟低的节点带宽垫底，配置写着 fake-ip 而 fake-ip 形同虚设，加了代理环境变量反而让请求变慢，静态检查全绿而 DNS 一直在漏。

所以最该带走的不是某一条命令，是那个习惯：别信声明，别信面板上的绿色，去测你真正在走的那条链路。
