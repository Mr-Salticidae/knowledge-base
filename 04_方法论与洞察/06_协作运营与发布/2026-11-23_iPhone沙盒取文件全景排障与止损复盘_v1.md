# iPhone 沙盒取文件全景排障与止损复盘

> 收口日期：2026-11-23。状态：**任务目标由“换平台找到同源资源”达成，非技术路径取件**；本文记录的是取件失败的全路径证据与止损判断。
> 一句话总结：**iOS 上“文件在下载列表里看得见”和“文件能被电脑读出来”之间隔着一整座沙盒城墙；先花 10 分钟做一个“源文件可获得性”的可行性探测，胜过两小时逐条试遍所有底层通道。**
> 证据范围：iPhone 11 Pro Max / iOS 18.1.1、Windows 11、本机单设备单次实战。所有失败均为该机该版本的实测，不能推广成所有 iOS 设备的定论。

## 结果与结论

目标文件《全民迷雾求生自由大世界规则书 V1.0.rar》由 UC 浏览器下载，在手机下载列表中可见，但**未能通过任何技术路径取出源文件**，最终由“其他平台找到同源资源”达成原始需求。iPhone 全程未越狱、未开开发者模式、未改任何系统设置，数据无损。

一句话归因：UC 浏览器的下载文件存在它自己的 **App 沙盒**里；而 iOS 18 对该 App 的容器访问请求返回 `InstallationLookupFailed`，把所有标准读取通道一次性封死。

## 目标与场景

- 需求：从 iPhone 取出 UC 浏览器下载的 rar → 复制到 Windows 桌面 → 解压 → 传回 iPhone 用“文件”App 直接阅读。
- 症结（作者中途点破）：UC 的“分享”只产出**它自己的链接**，不给源文件；在 UC 内解压要开会员。用户真正要绕开的是“在浏览器里解压”这一步。
- 设备：iPhone 11 Pro Max（iPhone12,5），iOS 18.1.1（22B91），USB 已配对；UC 浏览器 bundle id `com.ucweb.iphone.lowversion`（v19.3.1，App Store 安装，带 `lowversion` 后缀）。

## 取证路径全景（走了哪些路，各自撞在哪）

按“从浅到深”的顺序，把三个存储域和四类访问通道全部试过。这是本文最值钱的部分——一张可直接复用的“哪条路通、哪条死”地图。

| # | 路径 | 工具 / 命令 | 结果 | 关键证据 |
|---|---|---|---|---|
| 1 | MTP 照片域（Windows 资源管理器通道） | `win32com` 枚举 Shell Namespace | 通，但无目标 | “Apple iPhone → Internal Storage”挂载成功；递归扫 49 个 DCF 目录、3932 个文件，无任何 rar；`NameSpace(path)` 对 MTP 幻影路径返回 NULL，必须用 `ShellFolderItem.GetFolder` 递归 |
| 2 | AFC 媒体域 `/var/mobile/Media` | `pymobiledevice3 afc ls -r .` | 通，但无目标 | 21829 个文件全扫；严格过滤 `.rar` = **0 个**；`Downloads/` 下只有 `downloads.28.sqlitedb`（实为 App Store 下载库，非浏览器下载记录） |
| 3 | HouseArrest 容器直读（完整容器） | `pymobiledevice3 apps afc/pull --bundle-id ...` | **死** | 设备回 `The device refused to open the container ... InstallationLookupFailed` |
| 4 | HouseArrest 只读 Documents | `apps afc --documents` / `HouseArrestService.create(documents_only=True)` | **死** | 同上，同一堵墙 |
| 5 | App Group 容器 | 试 `group.com.ucweb.iphone.lowversion` | **死** | `No app with bundle ID ... is installed`（group id 不能当 bundle id vend） |
| 6 | RSD 加密隧道绕行 | `apps afc ... --userspace` | **死** | 隧道建立成功，但仍返回 `InstallationLookupFailed` —— 证明这是**设备端授权拒绝**，不是传输路径问题 |
| 7 | 精准备份（只备 UC 数据） | `backup2 backup --only-regex "ucweb" --full --unback` | **死** | 设备要求备份卷有 **>127.8GB** 可用（备份把每个硬链接/克隆按全尺寸计），本机 C 盘仅 100.6GB；且需设备输入锁屏密码。快照阶段 `SnapshotState=finished`，但 `BackupState=new`，未传任何数据 |
| 8 | 完整备份 | `backup2 backup --full` | **死** | 同上空间门槛 + 需密码，进程退出无输出 |
| 9 | 开发者通道直读容器 | `mounter auto-mount` / `developer core-device list-directory appDataContainer` | **死（未走通）** | `Developer Mode is disabled`；`amfi enable-developer-mode` 报 `Cannot enable Developer Mode while the device has a passcode set` —— 有锁屏密码就必须**在手机上手动开启并重启**，无法自动 |
| 10 | UC 内“分享”导出源文件 | 用户手机端操作 | **死** | 分享产物是 UC 自有链接，不是文件本体；作者明确这不是源 |

**结论**：三个存储域里，目标只在“App 沙盒”这个域；而访问沙盒的 4 类通道（HouseArrest、group、RSD 隧道、备份）在 **iOS 18 + 该签名形态**下全数被拒。这不是工具没装对，是系统层面的门。

## 关键判断与转折

- **配对成功 ≠ 有读权限**。iMazing CLI 能列出设备并显示 `paired`，pymobiledevice3 `usbmux list` 能拿到 UDID——但容器 vend 照样被拒。设备“认得你”和“给你数据”是两件事。
- **错误码要定位到“谁拒绝的”**。`InstallationLookupFailed` 出现在 lockdown 直连和 RSD 隧道两条完全不同的路径上，说明拒绝发生在设备端的服务层，换通信路径无用。搜到的同类资料也指出：该错误常见于 iOS 15–26 上非标准签名安装的应用，属预期行为。
- **`InstallationLookupFailed` 提示的是签名形态线索**。bundle id 带 `lowversion` 后缀、被系统判定为不可 vend，指向该 App 的容器访问受签名/特权限制；即便用户认定是 App Store 安装，也应以设备实测返回为准，不跟用户的记忆争论。
- **备份的隐藏门槛是“卷可用空间”而非“实际数据量”**。精准备份只挑 UC 数据，但设备仍按整机硬链接总尺寸要 119GB。单盘机器（本机只有 C 盘）天然卡死这条路，且 `--only-regex` 不能降低这个门槛。
- **开发者模式不是自动化的救命稻草**。有锁屏密码时必须人肉在设置里点开并重启——这是安全设计，不是工具缺陷。把它作为“需要用户配合”的选项，而不是默认路径。
- **最贵的成本是“没先问可获得性”**。真正省时的动作是开局就确认“这文件在别处有没有同源资源”，而不是等到所有通道试完才由用户提出。

## 复盘：做对了什么，哪里可以更快

- **做对：分层枚举而不是盲试**。先 MTP、再 AFC、再容器、再备份、再开发者通道，每层都留了命令和返回证据，才确认“目标只在沙盒”。这让止损有据，不是放弃。
- **做对：及时识破假路径**。两个“HIT”（`GUCA3292.JPG` / `PZUC9050.JPG`）只是文件名含 “UC” 的照片，非目标；没被关键词误报带偏。精准备份的 `downloads.28.sqlitedb` 也查明是 App Store 库而非下载记录，没有在错线索上深挖。
- **做对：用户点破症结后立刻改道**。作者一句“分享出来是链接、解压要会员”，直接把方向从“技术取件”切到“绕开浏览器解压”，避免了继续在分享功能里打转。
- **可更快：开局做可获得性探测**。应在动手连接设备前先问一句“这份资源是否全网可得 / 有无其他来源”。技术取件成本高、成功率受系统策略支配，**同源资源Substitution 的性价比永远更高**。
- **可更快：环境预检前移**。备份走到底才发现空间差 20GB、还要锁屏密码——这两项应在开工时（而非卡住时）核对。同理，开发者模式状态应在起手就查。
- **可更快：早用导出替代方案试探**。既然 UC 能“用其他应用打开”，第一步就该试能否把它导向一个支持文件共享的阅读器/网盘 App（那条路能绕开沙盒直读），而不是先钻底层通道。**本次因用户只找到“分享/打开”两项而作罢，但这是下次应优先验证的分支。**

## 如何使用：iOS 沙盒取件的决策顺序

下次遇到“iPhone 上某 App 里的文件要弄到电脑”，按此顺序，**先判可行性再动手**：

1. **先问可获得性（10 秒）**：这资源在别处有没有同源版本？有 → 直接取，结束。这一步优先级高于一切技术路径。
2. **判目标所在域**：MTP 照片域（相册/DCF）→ AFC 媒体域（`/var/mobile/Media`）→ App 沙盒。前两个能用 `pymobiledevice3 afc ls -r .` 和 Shell COM 免费扫；目标不在前两个，才确认“在沙盒”。
3. **优先导出替代方案**：试目标 App 的“用其他应用打开 / 存储到文件 / 分享到支持文件共享的 App”，把文件导出到一个可文件共享的容器，从这里读，绕开沙盒直读。
4. **再试标准容器读取**：`pymobiledevice3 apps afc/pull <bundle-id>`，同时试 `--documents`。若返回 `InstallationLookupFailed` 且 RSD 隧道同错 → 判定设备端拒绝，停止换路径。
5. **备份是最后手段，先做两项预检**：① 备份卷可用空间（设备按整机硬链接全尺寸算，可能要 100GB+，与“精准备份”无关）；② 设备是否需锁屏密码 / 备份是否加密。任一不满足就别启动。
6. **开发者通道需要人配合**：有锁屏密码则必须手机端手动开开发者模式 + 重启，事先征询用户，不作为默认路径。
7. **止损线**：同一错误码在两条不同通信路径复现、且确认是设备端授权拒绝 → 立即止损，回到第 1 步找替代资源，不继续堆工具。

## 环境备注（可复用的操作细节）

- `pymobiledevice3` 在 Python 3.13 上：清华源 `pip` 装不到，**改用阿里云镜像** `pip install -i https://mirrors.aliyun.com/pypi/simple/ pymobiledevice3` 成功；依赖是“套娃式”，需重复执行 `pip install` 直到无 `requires ... which is not installed` 提示。
- Windows 上 MTP 递归遍历必须用 Python `win32com.client.Dispatch("Shell.Application")` 的 `ShellFolderItem.GetFolder`；PowerShell 侧 COM 实例化会被安全策略拦截。
- AFC 的 `ls` 参数要传**相对路径**`.`/`DCIM`/`Downloads`，传绝对路径 `/` 会被误解析成本地盘符路径而报 `OBJECT_NOT_FOUND`。
- iMazing CLI 未激活时（`iMazing CLI is not activated`）所有设备文件命令不可用；GUI 免费版另说。iTunes 装完但 Apple Mobile Device Service 未注册时，需先启动 iTunes 才会触发设备以 AMDS 模式枚举并完成配对。
