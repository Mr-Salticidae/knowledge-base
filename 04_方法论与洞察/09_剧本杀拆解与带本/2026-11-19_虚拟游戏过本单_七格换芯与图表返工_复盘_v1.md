# 《虚拟游戏》过本单：七格换芯与三次图表返工

> 入档:2026-11-19
> 来源:私有剧本库 `juben-dm-lab` 的 `cases/954-虚拟游戏/`，一次完整生产（类型判定 → 七格落笔 → 图表定稿）
> 结论强度:内容侧单样本；图表侧为**流程性硬伤**（三次连踩同一根因），可直接入规范

## 一句话

一本四重真相的硬核本，套进了欢乐本的七格壳——**壳一格没改，芯全换**；内容一次成型，返工三轮全发生在「图怎么落地」，一次都没发生在「写什么」。

### 1.1 生产时间线

### 1.3 三次返工（全部在配图）

| 轮 | 我交出去的 | 用户看到的 | 病灶 |
| --- | --- | --- | --- |
| 1 | `relation-graph` 代码块（沿用库内既有格式） | 5,507 字符 JSON 源码铺满屏幕（截图反馈） | 私有 fence 只有特定工具认，预览器当普通代码块 |
| 2 | 改 `mermaid` flowchart `LR` | B 区跑到最左边，「先 B 后 A」 | dagre 按入边分层，B 区徐光无入边 → 被拉到起始列 |
| 2b | 改 `flowchart TB` + 子图内 `direction LR` | 仍是 B 在左 | 换方向只是换一种自动布局，不是控制 |
| 3 | Pillow 按固定坐标绘制 PNG | A 上 B 下，通过 | 定稿 |

另有两处小修，同样由肉眼发现：

- 名字旁的 `†`（dagger）被读成十字架，且与「灰底＝已死」图例自相矛盾 → 改文字标注 → 最终改红色斜线划掉，并补全漏标的 3 名死者（8 → 12）。
- 图例单行、固定 `x += 170` 步进，「红划＝已死 / 已亡」文字过长撞上线型说明 → 拆两行 + 按 `textlength` 动态推进。

## 二、判断区

### 判断一：模具是契约，内容是填充

七格的「壳」同时承担三件事：平台备案的格式预期、DM 台上翻页的肌肉记忆、跨本横向对比的基准。三者都与题材无关。所以跨类型复用时，动的是**第三格与第六格写什么**，不是格数与顺序。

| 格 | 欢乐本装什么 | 硬核本换成什么 |
| --- | --- | --- |
| ③ 复盘 | 加害网 + 互撕弹药 | 四重反转表（每重标「被哪条线索推翻」）+ 三起命案分层 |
| ⑥ 机制 | 敬酒 / 涨粉 / 换角 | 搜证 AP（4→4→3）+ 处决平票 + 定版时机 + 双结局判定 |

其余五格几乎原样通用——这反过来说明：**七格描述的是「开本要执行什么」，不是「这是什么类型的本」**。

### 判断二：内容可以用清单验收，呈现必须肉眼验收

清单查得出「有没有七格」「占比多少」「有没有第二个你」，查不出「B 区跑到左边」「这个符号什么意思」「图例压在一起」。三次返工、两次小修，**全部由用户的眼睛发现，没有一次是脚本报出来的**。

> 判据：凡生成物最终要被人看，验收就必须有一道「看」的动作，且看的是**最终载体**（PNG / PDF / 渲染结果），不是源码。

### 判断三：把布局决定权交给引擎，等于把确定性外包

Mermaid 的 dagre 按「入边分层」排布，它的目标是最小化交叉，不是复现我要的叙事顺序；无入边的节点会被推到起始列。给它的 `LR` / `TB` 参数只是**换一种自动布局**，不是控制点。

> 判据：当**顺序或位置本身承载信息**（分区、先后、层级、左右归属），用坐标画；只有「结构对就行、位置无所谓」时，才可以交给引擎。

### 判断四：状态标注优先用通用视觉惯例，不用自定义符号

`†` 三重失败：中文语境里被读成宗教符号；与「灰底＝已死」的图例逻辑冲突（该角色是金框）；把一个重要设定（已死但仍属六席、可投票）压缩成一个记号。

红色斜线划掉则是全世界都懂的「作废」。**图例只留一句话解释，符号本身自解释。**

### 判断五：字数红线按「正文口径」卡，但资源必须随仓库走

关系图的 JSON、图片引用不是 DM 会读的字。若把它们计入，6,000 字红线会被一张图冲垮，复盘占比也会被稀释到 40% 以下。

> 判据：结构化块（图代码块、JSON、图片引用、机器字段）不计入正文；分母用正文。
> 但反向义务同样硬：**图片必须随仓库分发**（`.gitignore` 开例外）。否则「合上就能开本」的自包含是假的——别人克隆下来图是断链。

## 三、可迁移判据（六条）

| # | 判据 | 触发场景 | 反例 |
| --- | --- | --- | --- |
| 1 | 复用体例先问「这格承载的是契约还是题材」 | 跨类型套模具 | 把硬核本压成欢乐本七格原装，推理链被打散 |
| 2 | 顺序/位置是信息时，坐标绘制；否则才交给引擎 | 分区图、流程图、时间线 | Mermaid 三次改方向仍不听 |
| 3 | 图表验收看最终载体，且放大局部看 | 任何要被人看的生成物 | 只看源码，漏掉 B 区在左、图例重叠 |
| 4 | 状态用视觉惯例（划掉、加粗、置灰），不用生造符号 | 死亡/作废/失效标注 | `†` 被读成十字架 |
| 5 | 图例多条目一律动态排版（按文字实测宽度推进） | 图例 ≥ 3 条 | 固定 `x += 170` 撞车 |
| 6 | 文档声明「自包含」时，先验证引用资源是否真的在库里 | 内嵌图片、附件的交付文档 | PNG 被 `*.png` 忽略，克隆即断图 |

## 四、未解问题

- **单样本**：硬核本换芯只跑了一本。情感本、机制本能否只换第三、六格，未验证；第七格「会员那句」在情感本是否仍然成立也未验证。
- **渲染器差异**：Mermaid 子图顺序在本机预览的表现，与 GitHub / Typora 是否一致未测——这也正是最终弃用它的理由之一，但不构成「Mermaid 一定不可用」的结论。
- **45.6% 是否偏高**：硬核本四重真相本身需要更长复盘，40–50% 区间的上沿可能是硬核本常态，而非写得太多。样本不足，暂不调红线。
