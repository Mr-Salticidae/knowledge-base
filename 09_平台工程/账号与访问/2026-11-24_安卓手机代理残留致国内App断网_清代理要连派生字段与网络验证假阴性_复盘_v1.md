# 安卓手机代理残留致国内 App 断网 · 清代理要连派生字段,别信 curl 的绿

> 入档:2026-11-24
> 来源:一句「链接我的手机,帮我更新棕色尘埃2」引出的三轮排障(小米 17 / Android 17 / USB 调试设备号 `c777ac0e`);电脑侧 Clash Verge,手机侧新装 Clash Meta for Android `v2.11.37.Meta`
> 状态:**已修复并双态验证**(Clash 开/关两种状态下抖音、番茄小说、Play 商店均正常);故障是排障过程中**我自己留下的系统设置**造成的,不是手机、运营商或 App 的问题

## 一句话

用 `adb shell settings put global http_proxy <电脑IP>:<端口>` 给手机临时挂过代理之后,只删 `http_proxy` **等于没删**——Android/MIUI 会把它拆成 `global_http_proxy_host` / `global_http_proxy_port` 等独立字段持久保存,系统联网探测因此一直去连一台已经不监听的电脑,超时 → 系统判定「此网络无互联网」→ 抖音、番茄小说这类**先看系统网络验证结果再发请求**的 App 全部转圈。而 `curl` 不读这层设置、照样 200,把故障伪装成「网络是通的,是 App 自己坏了」,让我连错三次归因,多花了约 25 分钟。

### 定位到的根因(实测证据)

- `adb shell settings list global | grep -i proxy` 在 `http_proxy` 已为 null 的情况下仍列出:`global_http_proxy_host=192.168.31.192`、`global_http_proxy_port=7897`、`global_http_proxy_exclusion_list=`、`global_proxy_pac_url=`
- `adb logcat`:`NetworkMonitor/205: PROBE_HTTP ... failed to connect to /192.168.31.192 (port 7897) ... after 10000ms` → `isCaptivePortal: isSuccessful()=false` → `ConnectivityService: [205 WIFI] validation failed`;移动数据网络 195 同样 failed
- `dumpsys connectivity`:Wi-Fi 的 Policies 里没有 `IS_VALIDATED`,只有 `ACCEPT_UNVALIDATED acceptPartialConnectivity`
- 同一时间 `adb shell curl https://www.baidu.com` 返回 200

### 修复动作(按顺序)

1. 逐个删除:`http_proxy`、`global_http_proxy_host`、`global_http_proxy_port`、`global_http_proxy_exclusion_list`、`global_proxy_pac_url`
2. **只做第 1 步 + 重启 Wi-Fi 不够**:18:50 的新一轮探测仍连旧代理并 failed(有对照记录)
3. 追加 `settings put global http_proxy :0`,再 `delete`,再重启 Wi-Fi → 18:51:20 起 `PROBE_HTTP ... time=125ms ret=204`、`isSuccessful()=true`,Wi-Fi 与移动数据均 validated
4. 「`:0` 触发了代理变更事件、让缓存旧代理的系统服务刷新」是**对第 2、3 步差异的推断**,未读系统源码求证;确定的是:做了这一步之后探测才恢复

## 如何使用

### 症状对照:什么情况该怀疑本文

- 手机**部分** App 转圈/报「网络出错」,而浏览器、`curl` 能打开网页
- Wi-Fi 图标上有叉或「已连接,但无法访问互联网」类提示;`dumpsys connectivity` 里对应网络没有 `IS_VALIDATED`
- 这台手机**曾经用 adb 设过 `http_proxy`**(哪怕已经删过)

### 三步定位(约 1 分钟)

```bash
ADB="/d/AIGC工作站/tools/android-sdk/platform-tools/adb.exe"

# 1. 看全部代理字段(不要只看 http_proxy)
"$ADB" shell settings list global | grep -i -E "proxy|pac"

# 2. 看系统探测到底在连谁——这一行是本案唯一决定性的证据
"$ADB" logcat -d | grep -i -E "NetworkMonitor|validation (failed|passed)" | tail -20

# 3. 看网络验证状态
"$ADB" shell dumpsys connectivity | grep "ni{WIFI" | grep -o "IS_VALIDATED" || echo "NOT validated"
```

### 清除与验收

```bash
# 清:5 个字段一个不留
for k in http_proxy global_http_proxy_host global_http_proxy_port \
         global_http_proxy_exclusion_list global_proxy_pac_url; do
  "$ADB" shell settings delete global "$k"
done
# 推一下系统服务(本案实测:缺这一步探测仍连旧代理)
"$ADB" shell settings put global http_proxy :0
"$ADB" shell settings delete global http_proxy

# 重连网络,让它重新探测
"$ADB" shell svc wifi disable; sleep 3; "$ADB" shell svc wifi enable; sleep 20
```

**验收不看 curl,看这三条:**

1. `logcat` 出现 `PROBE_HTTP ... ret=204` 且 `isCaptivePortal: isSuccessful()=true`
2. `dumpsys connectivity` 的 Wi-Fi 出现 `IS_VALIDATED`
3. 打开一个之前转圈的国内 App,截图确认内容真的加载出来

### 给手机临时挂代理的正确收尾

- 用完立刻按上面的 5 字段清单清,**当场验收**,不要留到下一轮
- 更省事的做法:手机上装 Clash Meta 用 TUN 模式,完全不碰 `http_proxy` 字段(本案最终方案),电脑端也不用开 `allow-lan`

## 回顾:为什么连错三次

### 1. 选错了「谁在说真话」

`curl` 200 是整场排障里最稳定、也最误导的信号。它稳定,是因为 curl 直接走 socket,根本不读系统 HTTP 代理设置,也不问「系统认为这个网络可不可用」;而 App 先问后者。**一个不经过故障点的测量工具,永远绿,而且永远没用**——和 ping 在 fake-ip 下自问自答是同一类陷阱。

真正该第一个看的 `logcat`,直到第三轮才抓。原因不是抓不到,是前两轮已经有了一个「说得通」的解释(服务被杀 / App 自身问题),没再去找反例。

### 2. 对照实验做了,但两组共用同一份污染

「Clash 开着报错、关着也报错 → 与代理无关」——推理形式没问题,漏在**变量选择**:开关 Clash 改变的是「代理服务在不在」,而残留字段在两组里都在。对照实验排除的只是你想到要动的那一个变量。

### 3. 测试输入没有取证

DNS 污染假说建立在两个我凭印象挑的域名上。没有抓 App 实际请求了什么,就用自己的猜测当被测对象;猜错了,后面所有对照都在验证一个不存在的问题,还顺手多改了一项系统设置(私人 DNS)。

### 4. 「修好了」的回执超出了验证范围

18:26 的回执写「问题定位到了,已经修复」,依据是 curl 200 + Play 商店截图。但 Play 商店走 VPN、curl 不经过故障点,**两个验证都绕开了坏掉的那条路**;受影响的国内 App 一个没测。用户 18 分钟后回来报「还是不行」,是这个缺口的直接后果。

## 可以带走的规律

| 规律 | 一句话 | 验证状态 |
|---|---|---|
| **清设置要清到派生字段** | 一条用户可见的设置项,底层可能是多条独立记录;删除入口项不等于删除它拆出去的字段 | ✅首验 |
| **测量工具要经过故障点才算数** | curl/ping 这类「直连底层」的工具,查不了「系统判定」层面的问题;先确定故障在哪一层,再选会经过那一层的探针 | 同族二次验证(前作是 ping 与 fake-ip) |
| **对照组不能共用污染背景** | 对照实验只能排除你动过的那个变量;自己改过的环境,要先列「我留下过什么」 | 同族二次验证(前作是「测试不投毒等于没测试」) |
| **回执的范围 = 验证的范围** | 写「已修复」之前,逐项核对故障报告里提到的每一个受影响对象,用会经过故障点的方式复测 | ⚠️首次 |
| **排障顺序:先日志,后假说** | 有系统日志可读时先读日志再立假说;一个「说得通」的解释会挡住去找反例的路 | ⚠️首次 |

## 未验证与保留项

- `put :0` 让系统刷新代理缓存的具体机制未读源码求证(见修复动作第 4 条)
- 私人 DNS(DoT,`dns.alidns.com`)在本机网络下不通的原因未查;已回退,不影响结论
- Clash 卡片锁定、系统自启动、电池「无限制」三项保活只做了当场验证,**没有经过真实重启或长时间待机的检验**
- Clash Meta 导入的是裸订阅,未单独核对国内分流规则;实测国内 App 在 Clash 开启下正常,但换节点或换订阅后的表现未知
