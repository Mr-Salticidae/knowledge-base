# 工位池塘:给自己的手机装一份,成为第一个真实测试员

> 入档:2026-11-20
> 来源:《工位池塘 Desk Pond》v0.7.1 上线后,把游戏装到本人手机(小米 25113PN0EC / Android 17 / adb `c777ac0e`)
> 状态:**安装成功并启动验证通过**;装的是从源码导出的本地签名自测包,非 TapTap 客户端分发版

## 一句话

游戏上线后想自己先当测试员,发现**「平台上能下载」和「我能 adb 装一份」是两条互不相通的路**:TapTap 上架走的是 TapPlay 沙盒,玩家端压根不给 APK 直下;最后靠源码重新导出一个原生包才装成。真正耗时的不是导出,是下载被截断、SDK 路径没配、MIUI 两道安全门——**每一道都在「以为成了」的地方又拦一次**。

## 事实记录(不可修改区)

- 项目:`github.com/Mr-Salticidae/desk-pond`,Godot **4.6**(本次本地导出所用版本;上架时工程为 4.6,见前作中的 4.7 记录以实际工程为准),2D 像素桌面陪伴工具
- 目标设备:小米 `25113PN0EC`,Android 17,USB 调试设备号 `c777ac0e`,此前未安装本游戏
- 平台侧实况:TapTap 应用 `1073282`,版本 `V-20261120` 已 `review_approved` + `published` / `status: online`
- 关键发现①:`webapiv2/apk/v1/list-by-app?app_id=1073282` 返回 `list: []`;`v3/button-flag` 返回的 `list: []` 为空 → **玩家端没有 APK 下载入口**
- 关键发现②:`package-management list-apk-packages` 后台有 APK `package_id 1084350`,`identifier: com.mrsalticidae.deskpond`,`30,519,192 B`,md5 `98fb59845a658dd4c0a39870d5db186a` —— 包体在后台存在,但不等于玩家能直取
- 玩家端商店页 `hidden_button: false`,`supported_platforms` 含 android/pc,但网页只有 TapTap **客户端**下载入口(`/download`),深链 `taptap://taptap.com/app?app_id=1073282`
- 本机缺件:无 Godot 编辑器、无导出模板、无自测签名密钥;Android SDK 在 `AppData/Local/Android/Sdk`(platform 32 + build-tools 30.0.2/32.0.0),JDK 17 在 `%ProgramFiles%\Java\jdk-17`
- 下载坑:`Godot_v4.6-stable_export_templates.tpz` 首轮 Python 流式下载只收到 `1,128,019,226 B`(应为 `1,251,639,300 B`),`zipfile` 报 `BadZipFile`;用 `curl -C -` 断点续传补齐 117 MB 后校验通过(35 entries)
- 产物:`desk-pond-build/build/DeskPond-v0.7.1.apk`,`29,753,260 B`,`aapt2 dump badging` → `name='com.mrsalticidae.deskpond' versionCode='2' versionName='0.7.1' application-label='工位池塘'`;`apksigner verify` v2/v3 通过、单一 signer
- 安装拦路:MIUI 对 adb 输入注入报 `SecurityException: Injecting input events requires ... INJECT_EVENTS`;对 adb 安装报 `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`,连 `adb shell pm install` 从设备侧安装也被同一策略拒绝
- 放行条件:用户本人在 **开发者选项 →「USB 调试(安全设置)/允许通过 USB 安装应用」** 打开后,同一条 `pm install -r` 立即 `Success`
- 验证:`firstInstallTime = lastUpdateTime = 2026-11-20 18:08:10`;`monkey -p com.mrsalticidae.deskpond` 启动后前台窗口为 `com.mrsalticidae.deskpond/com.godot.game.GodotAppLauncher`;截图显示竖屏主界面正常(水族馆 + 30 贝壳新手礼 + 甩杆按钮),logcat 无崩溃
- 数据来源:`taptap-cli` / Playwright 抓包 / `aapt2` / `apksigner` / `adb shell` / 真机截图

> 这一轮没有「发布胜利」可写——游戏早就上线了。真正的产出是**把一个只能在平台沙盒里玩的东西,变成自己手机上一个能点开、能测试的原生应用**。

## 回顾:四段,每段都被「以为成了」绊一次

1. **确认能不能从平台拿包**:后台能看到 APK,玩家端接口却是空列表、按钮位也是空。结论——TapPlay 沙盒游戏没有 APK 直下通道,「后台有包」不等于「玩家能取」。
2. **判断 adb 能不能直接装**:手机连着、TapTap 客户端也被深链拉到详情页,但 MIUI 拦了输入注入(`INJECT_EVENTS`),屏幕解锁也没用。于是放弃「在客户端里点下载」这条路。
3. **从源码自建原生包**:下载 Godot 4.6 编辑器(79 MB)+ 导出模板(1.25 GB,中途截断后续传),生成测试密钥,给构建副本改 `keystore/release_*`,配 `java_sdk_path`,导出+签名。工程里**原本就有 Android 预设**,不用新建。
4. **装到手机**:`adb install` 和 `pm install` 双双被 MIUI 的安装策略拒绝;用户开开关后,同一条命令立刻成功,启动、截图、日志三重验收通过。

顺序上唯一值得改的:**该先问「这游戏在玩家端到底有没有 APK」再动手找 adb 路径**。虽然结果一致,但先确认平台侧的分发形态,能更早排除「从 TapTap 客户端点一下就有」的捷径幻觉。

## 结果分析(两个视角分开写)

### 做到了什么、没做到什么

| 做到了 | 证据 | 没做到 | 诚实说法 |
|---|---|---|---|
| 手机上有可玩的原生应用 | 前台窗口 + 截图 + 无崩溃日志 | 拿到 TapTap 官方签名包 | 装的是本地测试密钥签名,签名体系与线上不同 |
| 包身份与线上一致 | 包名 `com.mrsalticidae.deskpond` / v0.7.1 / code 2 完全相同 | 与线上包**字节一致** | md5 不同(自签 + 本地构建),只能说「同一个应用的另一个签名版本」 |
| 竖屏布局适配 | 真机截图:池塘/水族馆/甩杆/任务苗圃齐全 | 全功能遍历 | 只看主界面,没逐项测存档、分享、二维码等分支 |
| 工具链留存可复用 | `godot-tools/` + `desk-pond-build/` 在工作区 | 第二台设备覆盖测试 | 只有一台真机,且尚未验证覆盖安装场景 |

**没有对照组,不写「获胜原因」。** 能写的是:每一次「以为成了」分别被哪一层拦下。

### 对照一:TapPlay 沙盒上线 vs 原生自测包——两条路的分叉

| 维度 | TapTap 上架版(TapPlay 沙盒) | 本地导出原生包 |
|---|---|---|
| 包从哪来 | 后台 APK `1084350`,玩家在客户端内运行 | `desk-pond-build` 源码导出 |
| 玩家端入口 | 无 APK 直下,仅客户端深链 | 常规安装,桌面图标 |
| 签名 | 作者 release 密钥(`D:/AIGC工作站/keys/deskpond-release.jks`) | 本地生成测试密钥 |
| 用途 | 面向玩家分发 | 本人真机自测 |
| 冲突点 | **同包名不同签名,不能互相覆盖** | 装正式版前须先卸载自测包 |

最该记住的一句:**同一个 `applicationId`,签名不同就是两个互不覆盖的应用**。Android 以包名判身份、以签名判更新资格;自测包能装,不代表将来能顺畅升到线上包。这条在同事把测试包发给别人时尤其容易踩。

### 对照二:三道「以为成了」的拦截

| 环节 | 以为 | 实际 | 判据 |
|---|---|---|---|
| 平台拿包 | 后台有 APK = 能下载 | 玩家端 `list-by-app` 为 `[]`、按钮位为 `[]` | 后台包体库与玩家分发开关是两套状态 |
| 模板下载 | Python 流读完 = 下完 | 只有 1.128/1.25 GB,`BadZipFile` | 下载类任务一律以**目标字节数或 zip 校验**收尾,不以「循环正常退出」收尾 |
| 装到手机 | `adb install` 失败换 `pm install` 就行 | 两者同报 `INSTALL_FAILED_USER_RESTRICTED` | 系统级策略拦的是「通道」,换命令不换通道就没用;只能授权放行 |

第三条的边界要说清:**这不是可以技术绕过的问题,是设备所有者的授权问题**。MIUI 把 adb 安装和输入注入都归到同一组安全开关下;不授权就没有合法安装路径,正确的动作是请本人开开关,而不是找提权技巧。

## 方法论沉淀

### 沙盒上架与原生自测是两条独立路径,不要假设它们共享分发通道

**核心**:一个游戏在平台上架成功,只证明「平台认可这份包并可分发」;它不保证你能从平台把包取出来装到自己的测试机上。TapPlay/沙盒类上架尤其如此——平台把运行放在自己的客户端里,玩家端刻意不暴露 APK。

**来源**:后台 `list-apk-packages` 明明有 `1084350`,但玩家端 `apk/v1/list-by-app` 返回空、`button-flag` 返回空;深链只能把 TapTap 客户端拉到详情页,给不了安装文件。最后是源码导出解决的。

**验证状态**:⚠️ 首次(单平台单次,Android 沙盒形态)。

**操作规则**:
1. 想给自己装一份,先分清目标应用是「原生 APK 分发」还是「平台沙盒运行」——查玩家端 APK 列表接口比看后台包体库准。
2. 沙盒类一律假定「取不到包」,直接走源码导出,别在客户端里找下载按钮浪费时间。
3. 自测包与线上包同包名不同签名时,在文件名和文档里标注 `self-signed`,并写明「升级前先卸载」。

**反例·边界**:若平台提供了测试二维码/内测分发码(小游戏/H5 有,APK 没有),优先用官方测试入口——那才是「和玩家完全一致」的包。本次 `get-test-qr-code` 对 APK 明确返回不适用,才走源码路线。

### 大文件下载要以字节数或格式校验收尾,不以程序没报错收尾

**核心**:流式下载循环「正常跑完」只说明读到过 EOF,不说明内容完整。CDN 中断、网关截断都会给出一个静默缺尾的文件,而 Python 的 `urllib` 不会为「比 Content-Length 少一截」抛异常。

**来源**:导出模板首轮收 1,128,019,226 B,API 标称 1,251,639,300 B,差 117 MB;`zipfile.ZipFile` 直接 `BadZipFile: File is not a zip file`。`curl -C -` 续传补齐后 `valid zip, entries: 35`。

**验证状态**:⚠️ 首次,但这是通用型教训,任何大体积产物都适用。

**操作规则**:
1. 下载前先拿到标称大小(HTTP `Content-Length` 或 API 的 `size`),下载后 `stat -c%s` 对账;不等就视为失败。
2. 对 zip/tpz/apk 这类容器格式,下载后立即做一次结构校验(`zipfile.ZipFile` 打开、`apksigner verify`),比比对 md5 更早发现问题。
3. 失败时用 `curl -C -` 断点续传,比重下省时间;续传前确认服务端支持 Range。

**反例·边界**:HTTP 压缩传输会让实际落盘字节小于 `Content-Length`;此时以「文件能被容器格式打开」为准,而不是死磕字节数。

### 系统级安全门拦的是通道,换命令等于原地打转

**核心**:`adb install` 被拒后改用 `adb shell pm install`,看似换了路径,其实仍走同一套系统安装策略,所以拿到完全相同的错误码。分辨「这是命令的问题还是策略的问题」,看错误码是否在换通道后变化。

**来源**:MIUI 连报 `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`,从宿主机和从设备侧都一样;输入注入也报 `INJECT_EVENTS` 权限不足。用户在开发者选项打开「USB 调试(安全设置)/允许通过 USB 安装应用」后,同一条 `pm install -r` 立刻 `Success`。

**验证状态**:⚠️ 首次(单设备 MIUI/HyperOS)。

**操作规则**:
1. 权限类错误先看错误码语义:`INSTALL_FAILED_USER_RESTRICTED` / `SecurityException: INJECT_EVENTS` 都是「设备所有者未授权」类,不是命令写错。
2. 换命令最多试一次用于确认错误码不变;不变就停止重试,直接走授权路径,不要反复触发拒绝。
3. 授权属于不可逆控制权的让渡,必须由用户本人操作;AI 只给出精确的开关路径和验证步骤,不尝试绕过。

**反例·边界**:`INSTALL_FAILED_INSUFFICIENT_STORAGE` / `INSTALL_PARSE_FAILED_*` 是命令和包本身的问题,换通道或修包有意义,不适用本条。

## 下次改进

**如果重来,最想改哪一步**:先问平台的玩家端分发形态,再决定要不要导出原生包。虽然这次没有多走很多冤枉路,但「后台有包 → 应该能取」这个假设是最先该被证伪的。

**下次同类型任务的行动清单**:

1. 先查玩家端 APK 列表/按钮接口,确认是原生分发还是沙盒;沙盒一律按「取不到包」处理。
2. 建构建副本再改导出配置,不动原仓库的预设和密钥路径。
3. 大文件下载完成立刻对字节数 + 开一次容器结构校验;缺口用 `curl -C -` 补。
4. 自测包用独立测试密钥签名,文件名标注 `self-signed`,文档写明与线上包不可互相覆盖。
5. MIUI/类似定制系统遇到 `INJECT_EVENTS` / `INSTALL_FAILED_USER_RESTRICTED`,停止重试,给出开关路径请用户本人授权。
6. 装完三重验收:`pm list packages` / `dumpsys package` 版本 / `monkey` 启动后 `mCurrentFocus` + 真机截图 + logcat 崩溃检查。

## 附记:只在真跑时才现形的坑

| 现象 | 真因 | 判据 |
|---|---|---|
| 玩家端没有下载按钮 | 该游戏走 TapPlay 沙盒,平台不暴露 APK | `apk/v1/list-by-app` 返回 `list: []`,`button-flag` 的 `list` 也为空 |
| 导出的 tpz 不是 zip | 首轮下载被静默截断,少 117 MB | API 标称 1,251,639,300 B 对实际 1,128,019,226 B;`curl -C -` 补齐 |
| `Cannot export ... 编辑器设置中需要有效的 Java SDK 路径` | Godot 用户配置的 `export/android/java_sdk_path` 为空 | 写 `editor_settings-4.6.tres` 的该项为 JDK 17 路径(注意本机是 `%APPDATA%` 而非 Steam 便携版目录,见前作) |
| `Could not find version of build tools that matches Target SDK, using 30.0.2` | 工程 target 35,本机只到 32 | 只是降级提示,不阻断导出;签名和 badging 校验通过即可 |
| Git Bash 下 `adb push ... /data/local/tmp/x` 变成 `C:/Program Files/.../data/local/tmp` | MSYS 路径转换把 POSIX 路径翻成 Windows 路径 | `export MSYS_NO_PATHCONV=1`,并用 `adb shell ls` 在设备上二次确认 |
| `adb install` / `pm install` 同报 `INSTALL_FAILED_USER_RESTRICTED` | MIUI USB 安装策略未放行,换命令没换通道 | 用户在开发者选项打开「允许通过 USB 安装应用」后成功 |
| `adb shell input keyevent` 报 `SecurityException: INJECT_EVENTS` | MIUI 未授权 adb 输入注入,屏幕解锁也无用 | 不依赖点击,改用深链 `am start` + adb 安装;确需点击时请用户本人操作 |
